# Auditoría de seguridad y preparación de EduPro

Fecha: 5 de octubre de 2026. **Resultado: no aprobado para tratar información nacional de estudiantes en producción.** Hay correcciones locales y pruebas reproducibles, pero siguen abiertos controles críticos de autorización, recuperación y operación. Completar una auditoría no equivale a haber eliminado todos sus hallazgos.

Se revisaron Flutter, Cloud Functions, Firestore, Storage, dependencias y configuración remota de Firebase. Las consultas remotas fueron de solo lectura de configuración: no se descargaron expedientes, listados de usuarios ni objetos privados, no se probaron ataques en producción y no se desplegaron cambios. El repositorio tenía numerosos cambios previos que se conservaron. No se recibieron cuentas ficticias ni un entorno de staging confirmado para pruebas completas de login.

## Hallazgos de mayor prioridad

1. **Recuperación sin configurar, confirmado remotamente.** La base `(default)` informa `POINT_IN_TIME_RECOVERY_DISABLED`, `DELETE_PROTECTION_DISABLED` y retención de versiones de 3600 segundos. La consulta de calendarios de backup devuelve una lista vacía. Esto verifica ausencia de backups programados de Firestore; no demuestra que no existan exportaciones manuales externas. No se hizo una restauración. La replicación no sustituye un respaldo ante borrado o corrupción lógica. [Recuperación de Firestore](https://firebase.google.com/docs/firestore/disaster-recovery).
2. **MFA todavía evadible por acceso directo a datos.** Se retiró el bypass del cliente y se reforzaron las funciones, pero Firestore/Storage no exigen una sesión que acredite el segundo factor. La configuración real de Auth informa MFA nativo `DISABLED`; las 16 funciones inspeccionadas tienen `DISABLE_TWO_FACTOR=true` en el entorno desplegado. La presencia de esa variable no prueba por sí sola cómo la interpreta el binario publicado; requiere retirar/verificar el bypass al desplegar. No basta con mostrar un diálogo en Flutter.
3. **App Check incompleto, confirmado remotamente.** Firestore, Storage y Authentication informan `UNENFORCED`. Las funciones tienen `ENFORCE_APPCHECK=true` configurado, pero no se comprobó su rechazo efectivo mediante llamadas reales. El cliente lo deja desactivado por defecto si no recibe los defines de compilación. Coordinar proveedores, clientes y enforcement antes de activar producción.
4. **Escalada de privilegios y accesos indebidos corregidos localmente.** Incluían añadir `teamRole` al perfil, adquirir rol docente con un registro pendiente, apropiarse de un índice de alumno de otro colegio y usar un correo no verificado como identidad. Las reglas desplegadas difieren de las locales; la versión remota de Firestore aún contiene 18 usos de `changedKeys()`. No se ha verificado cada vulnerabilidad contra el servicio real ni se ha desplegado su corrección.
5. **Confidencialidad dentro de cada colegio aún insuficiente.** Persisten lecturas de padrones completos por docentes en determinados módulos y adjuntos de chat accesibles a integrantes del colegio sin comprobar participación en el hilo. Debe definirse autorización por alumno, tutor, curso, asignatura y conversación, además de por colegio.
6. **Dependencias y calidad pendientes.** Se aplicaron actualizaciones npm compatibles y se agregaron pruebas. Quedan avisos de dependencias y errores del analizador. El build web puede compilar porque no incluye todos los archivos de `lib/`; no significa que todo el repositorio esté libre de errores.

## Correcciones entregadas y compatibilidad

- [Reglas](audit-rules.md): `affectedKeys`, membresías aprobadas, correo verificado en fallbacks, aislamiento de índices, calificaciones/entregas, revocación y subidas de chat sin sobrescritura. Hay consecuencias de compatibilidad: docentes sin asignaturas/grados cargados y cuentas sin correo verificado necesitarán regularización antes del despliegue.
- [Backend](audit-backend.md): autorización previa a mutaciones de Auth, validación de IDs, límites de solicitudes, TOTP con transacciones/TTL/replay, mejores contraseñas nuevas y logging más discreto. Recuperación de factor aún pendiente; no se permite sustituir un factor activo solo con contraseña.
- [Cliente](audit-client.md): roles desconocidos sin privilegios, rutas administrativas protegidas, endpoints MFA correctos y revalidación tras reautenticación, enlaces seguros en puntos revisados, cierre de sesión al fallo y pruebas de pantalla pequeña.
- Hosting incluye cabeceras básicas y el HTML declara idioma. No se habilitó una CSP completa que pudiera romper Flutter/OAuth sin pruebas de navegador.
- Scripts de pruebas, escaneo local de secretos y consulta remota de metadatos quedan disponibles en `scripts/` y `security-tests/`. Los reportes `.log` son locales/ignorados; no contienen expedientes.

## Evidencia reproducible

Los resultados definitivos se resumen en [security-audit-results.json](security-audit-results.json). **Pasaron 37 pruebas locales: 20 de reglas, 13 del backend y 4 de Flutter. La compilación web pasó.** El analizador completo no pasa: registra 215 errores dentro de 1179 incidencias. No se ejecutó login de extremo a extremo ni se certifica producción. Los detalles de las regresiones corregidas están en los informes por área.

```powershell
node --test functions/test/security.test.js
flutter test --no-pub
flutter build web --no-wasm-dry-run
flutter analyze --no-pub
npm run test:rules
npm run audit:secrets
npm audit --json
npm --prefix functions audit --json
```

Las pruebas de reglas requieren Java 21 y Firebase CLI. Usan únicamente `demo-edupro-security` y puertos loopback 8088/9198; rechazan un proyecto/host diferente. Los tests de backend no conectan con Firebase real. La consulta de metadatos `scripts/audit-cloud-security.cjs` requiere la sesión existente de Firebase CLI y reutiliza su instalación local de Windows; no es un script portable de CI ni lee datos escolares.

## Condiciones antes de un lanzamiento con datos reales

1. Configurar recuperación y comprobar una restauración separada; designar responsables y aprobar retención/RPO/RTO.
2. Resolver MFA en la frontera de datos y retirar bypasses efectivos; validar revocación y mínimo privilegio por colegio/persona/conversación. Coordinar enforcement App Check con una compilación que tenga proveedores configurados.
3. Preparar staging con datos ficticios, regularizar membresías/asignaciones/correos y pasar pruebas E2E de login/roles/pagos/errores. Resolver endpoints ausentes y avisos relevantes de dependencias.
4. Revisar IAM/cuentas de servicio, alertas, cuotas, retención de logs, privacidad de adjuntos/cachés y requisitos legales; medir carga representativa sin atacar producción.
5. Desplegar versiones revisadas de reglas, Functions y cliente en una ventana controlada, volver a consultar configuración y efectuar pruebas posteriores. Las correcciones de esta auditoría todavía no protegen el despliegue actual.

Si ya existen expedientes reales, los hallazgos críticos requieren priorizar contención y revisión de accesos por el responsable del servicio. Esta auditoría no obtuvo ni alteró esos expedientes ni acredita que haya ocurrido una intrusión.
